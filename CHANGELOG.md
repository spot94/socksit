# Изменения

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/);
проект придерживается [семантического версионирования](https://semver.org/lang/ru/).

## [Не выпущено]

### Исправлено

- **SocksIt больше не мешает подключиться корпоративному VPN.** С глобальным fake-ip (0.3.0)
  клиент VPN получал синтетический адрес своего же шлюза — а он намеренно ходит мимо
  виртуальных адаптеров, иначе туннель нёс бы сам себя. Пакеты уходили на `198.18.x.x` через
  физический интерфейс, где этот адрес не значит ничего. Cisco AnyConnect писал «Unable to
  contact <шлюз>» и «Connection attempt has failed due to server communication errors»,
  FortiClient ломался так же, и лечилось это только остановкой службы — то есть выглядело
  как «SocksIt ломает VPN», без единой строчки в наших логах.

  Маршрутизацией это не чинится: клиент попросту не отдаёт нам пакет. Поэтому служба теперь
  сама находит шлюзы установленных VPN-клиентов и держит их имена вне fake-ip: профили Cisco
  AnyConnect / Secure Client, туннели FortiClient в реестре и общая телефонная книга RAS
  (встроенный VPN Windows). Список пишется в журнал при изменении и виден в «Диагностике»;
  в `socksit.yaml` он не сохраняется — это свойство машины, а не настройка.

  Найденные шлюзы остаются исключением даже при `direct_domains: []`: пустой список означает
  «свои имена не задаю», а не «сломай другой туннель».

- **Результат «Проверить прокси» больше не появляется за пределами экрана.** Ответ печатался
  в общий баннер в самом низу раздела настроек — под списком приложений, исключениями и
  блоком конфига с сервера, — поэтому после нажатия кнопки на видимой части экрана не менялось
  ничего, и до результата надо было догадаться пролистать. Теперь ответ появляется прямо под
  кнопкой, в той же карточке «Подключение», а результат сохранения — рядом с закреплённой
  кнопкой «Сохранить и применить», которая всегда на виду.

  Заодно: кнопка проверки блокируется на время опроса (он занимает секунды, и второй клик
  гонялся с первым), а сохранение стирает прошлый вердикт — он мог относиться к прежнему
  адресу прокси.

## [0.3.0] — 2026-08-24

### Добавлено

- **Bypass-подсети (`bypass_cidrs`)** — перечисленные диапазоны исключаются из туннеля
  целиком: для них ставятся более специфичные маршруты через физический шлюз, которые
  выигрывают у `0.0.0.0/0` по longest-prefix-match независимо от метрики. Реализовано
  через `route_exclude_address` на TUN-интерфейсе плюс страховочное правило маршрутизации
  в direct.

  Значения по умолчанию (работают из коробки, настройка не требуется):
  `127.0.0.0/8`, `169.254.0.0/16`, `224.0.0.0/4`, `255.255.255.255/32`. Диапазон роутерного
  FakeIP (`198.18.0.0/15`) в дефолт НЕ входит — см. «Изменено» ниже.

  Настраивается ключом `bypass_cidrs` в `socksit.yaml` и командами
  `socksit config bypass add|rm|list|reset`. Отсутствие ключа = значения по умолчанию,
  `bypass_cidrs: []` = отключить их.

- **Прямые домены раздаются с конфиг-сервера.** В профиле появилось поле «Прямые домены»,
  фид несёт ключ `direct_domains`, а клиент в режиме `override` объединяет его со своим
  списком через `managed_domains` — ровно как уже сделано для приложений и подсетей. Без
  этого исключение по имени пришлось бы вбивать руками на каждой машине, хотя именно оно
  чинит заблокированный эндпоинт.

  Пустое поле на сервере = «ничего не навязываем» (ключ не попадает в фид), а не «очистить
  список». Для приложений и подсетей пустое поле очищает вклад канала, здесь — нет:
  пустой список доменов означал бы «не исключать ни одного имени» и снёс бы встроенные
  исключения, включая проверочные имена Windows, по которым система решает, есть ли
  интернет.

- **`direct_domains` — имена, которые никогда не идут через прокси.** Раньше исключить
  назначение можно было только по IP (`direct_subnets`), а с fake-ip соединение несёт имя,
  а не адрес — то есть по IP оно и не матчится. Теперь имя из списка не получает fake-ip
  **и** маршрутизируется напрямую даже для проксируемого приложения (имя берётся из SNI,
  поэтому работает и для соединения, набранного по IP). Нужно, когда конкретный эндпоинт
  отказывает именно с адреса прокси: анти-DDoS или гео-фильтр дропает SYN с хостингового
  IP, приложение висит, а в «Статистике» видно «отправлено N КБ, получено 0». Рецепт
  диагностики — в README. Правится в панели («Прямые домены») и командой
  `socksit config domain add|rm|list|reset`.

  По умолчанию, кроме mDNS/интранет-суффиксов, в список входят проверочные имена Windows
  (`.msftncsi.com`, `.msftconnecttest.com`): fake-ip выдаётся всей машине, а NCSI сравнивает
  ответ для `dns.msftncsi.com` с фиксированным адресом — синтетический адрес заставляет
  Windows сомневаться в наличии интернета.

- **DNS проксируемых приложений больше не резолвится локально** (`dns.fakeip_all`,
  включено по умолчанию). Раньше fake-ip выдавался по правилу «процесс = приложение из
  списка», но на Windows DNS-запрос отправляет служба DNS Client, а не приложение —
  правило не срабатывало **никогда**, и запрос уходил в локальный резолвер. Следствия:
  утечка имён в локальную сеть; адреса выдавались близкие к пользователю, а выход шёл
  из прокси (не тот CDN-узел, часть сервисов работала криво); в корпоративной сети —
  внутренние адреса, недостижимые со стороны прокси. Теперь fake-ip выдаётся всем
  запросам, поэтому имя доезжает до прокси и резолвится на его выходе, а маршрутизация
  по-прежнему решает прокси/напрямую по процессу (для direct движок сам перерезолвит имя
  локально). Исключения: суффиксы `dns.direct_domains` (mDNS/интранет) и собственное имя
  прокси. По той же причине отказ AAAA стал глобальным — по процессу он тоже не
  срабатывал.

- **График трафика в «Обзоре»** — две линии: всего через туннель и через прокси. Скорость
  за последние 5 минут с замером каждые 2 с; история хранится в памяти панели и начинается
  заново при переоткрытии окна. Общая линия считается по монотонным счётчикам движка;
  проксируемая — по дельтам отдельных соединений (у API нет накопительного счётчика по
  outbound), поэтому соединения, успевшие и появиться и исчезнуть между двумя замерами,
  в неё не попадают.

- **Переключатель «Проксировать весь трафик»** (`proxy_all`) — весь трафик идёт через прокси,
  список приложений игнорируется; прямые подсети и `bypass_cidrs` продолжают действовать.
  Локальный, как «Значок в трее»: управляемый конфиг его не несёт и не может включить
  удалённо. В панели при включении список приложений блокируется и гаснет.

- **Ошибки соединений в журнале теперь называют приложение.** Движок в таких строках
  сообщает только внутренние адреса туннеля (`172.19.0.1:<порт>->172.19.0.2:<порт>`), из-за
  чего нельзя было отличить «приложение само сбросило соединение» от «перезапустился
  туннель». Служба сопоставляет порт с процессом через Clash API и дописывает в строку
  `[app: claude.exe]`. Не удалось сопоставить — строка остаётся как есть.

- **Фильтры по столбцам в «Статистике»** — под заголовками появилась строка фильтров
  (процесс / назначение / сеть / через), работающих вместе с общим поиском по логике И,
  плюс кнопка сброса.

### Исправлено

- **Обновление управляемого конфига больше не сбрасывает настройки, описывающие сеть самой
  машины.** В режиме `replace` конфиг собирается из фида заново, поэтому всё, чего фид не
  несёт, возвращалось к значениям по умолчанию. Для двух ключей это не сброс, а отказ:
  `bypass_cidrs` описывает роутер перед машиной (FakeIP-роутер раздаёт адреса, понятные
  только ему) — после обновления фида этот трафик уходил в никуда, и выглядело это как
  «ничего не менял, перестало работать»; `direct_domains` — это то место, где живёт
  эндпоинт, отказывающий адресу прокси, и его потеря снова ломала приложение, максимум
  через час. Теперь `bypass_cidrs` сохраняется всегда (фид его не несёт по смыслу), а
  локальные `direct_domains` — когда сервер о них ничего не говорит.



- **`check_interval` наконец означает то, что написано.** Расписание проверок держалось на
  одном длинном таймере, а таймер меряет время работы процесса. На машине, которую выключают
  на ночь, суток непрерывной работы не набирается никогда, поэтому 24-часовой интервал не
  срабатывал ни разу: фактически проверка шла при каждом старте службы, через 30 секунд после
  включения. Пять перезагрузок за день — пять проверок; интервал в 7 дней не значил ничего;
  а в режиме `auto` обновление могло начать устанавливаться через полминуты после включения
  ПК, перезапуская службу ровно тогда, когда человек садится работать.

  Теперь отметка последней проверки хранится на диске (`update-state.json`), а служба раз в
  5 минут сверяет её с календарными часами. Один и тот же интервал соблюдается и при
  перезагрузках, и при пробуждении из сна; изменение интервала в настройках вступает в силу на
  ближайшем тике, а не после срабатывания старого таймера. Неудачная проверка повторяется через
  15 минут, а не молчит до конца интервала. Ручная кнопка «Проверить сейчас» сдвигает расписание,
  как обычная проверка.

- **В режиме `auto` неудачная попытка больше не зависит от того, выключают машину или усыпляют.**
  Версия, которую auto уже пробовал установить, хранилась в памяти службы: ПК с перезагрузками
  пробовал заново при каждом включении, а ноутбук, который только спит, не пробовал никогда —
  сорванная по таймауту закачка означала, что обновления для него больше нет. Теперь попытка
  записывается на диск, и повтор той же версии разрешён через 6 часов независимо от того, как
  машину используют.

- **Канал управления больше не может залипнуть навсегда.** DACL канала пересвязывается,
  когда в системе появляется интерактивный пользователь (см. запись про панель из трея).
  Закрытие прежнего слушателя в go-winio ждёт свою внутреннюю горутину, а та может остаться
  в ожидании клиента, который уже не придёт: если короткий RPC отключается ровно в момент
  закрытия, попытка соединения падает с `ERROR_NO_DATA`, повтор снова уходит в ожидание — а
  сигнал закрытия уже израсходован. Под нагрузкой воспроизводится примерно раз на двадцать
  пересвязываний.

  Делает это супервизор канала, поэтому зависание оставляло службу без канала управления до
  перезапуска: панель к ней больше не подключалась, и попросить службу повторить попытку было
  нечем. Теперь пересвязывание не блокируется на закрытии (2 с на штатное завершение), а если
  новый слушатель создать не удалось — поднимается прежняя привязка, и служба остаётся
  достижимой; причина уходит в лог предупреждением.

- **«Конфиг ещё не валиден: field bypass_cidrs not found» после обновления.** Разбор
  конфига отвергал любой незнакомый ключ. Как только более новая версия дописывала в
  `socksit.yaml` новый ключ (первым таким стал `bypass_cidrs`), любой компонент постарше —
  панель, запущенная из старой копии exe, откат на предыдущую версию, фид от более нового
  конфиг-сервера — переставал читать конфиг целиком: служба отказывалась применять
  собственный файл, проксирование останавливалось, а панель показывала «Конфиг ещё не
  валиден».

  Теперь незнакомые ключи игнорируются (конфиг совместим вперёд и назад), но не
  замалчиваются: `socksit config validate` и «Диагностика» показывают их предупреждением —
  это либо опечатка, либо запись от более новой версии.

- **Панель, открытая из трея, работала только после перезапуска от администратора.**
  DACL канала управления строился один раз при старте службы, а служба стартует **до входа
  пользователя**: консольной сессии ещё нет, `WTSQueryUserToken` не срабатывает, и молча
  использовался фолбэк — SID **SYSTEM**. В результате канал оставался доступен только
  Administrators на всё время работы службы: обычная панель не получала статус туннеля
  (показывала, что проксирование не работает), не могла сохранить настройки и управлять
  службой. Теперь канал **пересвязывается** под интерактивного пользователя, как только он
  появляется (и при смене пользователя), а бессмысленный фолбэк на SYSTEM убран.

- **Таблица «Статистики» и журнал теперь тянутся по высоте окна** — вместо фиксированной
  доли viewport (`56vh`/`60vh`), из-за которой снизу оставалась пустая полоса на высоких
  окнах и таблица обрезалась на низких.

- **Проксируемое приложение больше не может уйти в обход по IPv6.** Датаплейн работает
  только по IPv4 (в TUN нет IPv6-адреса), поэтому приложение из списка, получившее AAAA,
  соединялось с целью **вне туннеля**: без прокси, без покрытия kill-switch и без следа в
  «Статистике» — внешне выглядело как «приложение вообще не обрабатывается». Теперь
  проксируемому набору AAAA отклоняется, и приложение откатывается на IPv4, попадая в
  туннель.

- **Повторная установка больше не обнуляет `sing-box.exe`.** «Удалить» снимает только
  регистрацию службы — файлы в `C:\Program Files\SocksIt\` остаются. При повторном
  «Установить» движок копировался сам в себя (источник и приёмник — один и тот же файл), а
  `os.Create` обрезает файл **до** чтения: получался `sing-box.exe` на 0 байт и ошибка
  «не является приложением Win32». Теперь копирование отказывается работать с файлом в
  себя, идёт через временный файл с переименованием (прерванное копирование не портит
  прежний файл), пустой движок считается отсутствующим и до-качивается, а установка не
  регистрирует службу вокруг непригодного движка.

- **Смена fake-ip диапазона больше не оставляет мёртвый кэш.** Постоянное хранилище
  fake-ip (появилось вместе с `cache.db`) движок загружает не сверяя записи с текущим
  диапазоном: после переезда `240.x` → `198.18.x` приложениям продолжали отдаваться
  адреса из старого диапазона, к которым **нет маршрута** — `auto_route` не расщепляет
  `240.0.0.0/4`, поэтому такие пакеты уходят в физический шлюз и умирают. Симптом —
  «нет соединения» в приложении, которое не лечится ни перезапуском приложения, ни
  перезапуском службы. Теперь при смене диапазона служба очищает `cache.db` и пишет об
  этом в лог.

- **Приложение пропадает из «Статистики» и начинает работать только после его
  перезапуска.** Таблица соответствий fake-ip жила только в памяти движка, поэтому любой
  перезапуск движка (сохранение настроек, обновление управляемого конфига, смена сети)
  обнулял её. Приложение, закэшировавшее выданный ранее fake-ip адрес, после этого било в
  адрес, про который новый движок ничего не знает: трафик никуда не шёл и в статистике не
  появлялся, пока не перезапустишь само приложение.

  Теперь состояние движка сохраняется на диск (`experimental.cache_file` со
  `store_fakeip`, файл `%ProgramData%\SocksIt\cache.db`) — соответствия переживают
  перезапуск, и перезапускать приложения больше не нужно.

- **«Повисший» значок в трее после включения компьютера.** Служба запускала трей, как
  только появлялся пользовательский токен — то есть ещё на экране входа, до старта
  `explorer.exe`, который владеет областью уведомлений. Регистрация значка
  (`Shell_NotifyIcon`) в этот момент штатно завершается таймаутом, библиотека трея
  начальную попытку не повторяет: процесс оставался жив, но без значка и меню — пустая
  иконка, не реагирующая на нажатия, — и при этом удерживал синглтон, поэтому служба его
  не перезапускала.

  Теперь трей запускается только после того, как в целевой сессии поднялся и «устоялся»
  (5 c) shell, а сам трей завершает работу, если значок не зарегистрировался за 30 c —
  служба поднимает его заново уже в готовой сессии.

- **Совместимость с роутерным прозрачным проксированием по FakeIP.** Если роутер
  (OpenWrt + Podkop/sing-box, mihomo, clash) отдаёт синтетические адреса из
  `198.18.0.0/15`, SocksIt перехватывал их своим маршрутом по умолчанию и уводил в TUN
  вместо роутера — сайты из «туннельных» списков роутера переставали открываться
  («Connection refused»), пока служба запущена. Лечится исключением `198.18.0.0/15` из
  туннеля — включается двумя ключами явно (рецепт в README); по умолчанию не трогаем,
  чтобы не навязывать смену собственного fake-ip всем (см. «Изменено»).

### Изменено

- **Раздел «Настройки» перестроен.** Была одна карточка без заголовка, где в общей сетке лежали
  подключение к прокси, политика маршрутизации, исключения и переключатели интерфейса, причём
  пояснений не было ни у одного поля — тексты для них существовали в переводах, но показывались
  только как всплывающая подсказка. Теперь поля разложены по озаглавленным группам
  «Подключение» / «Что проксировать» / «Исключения» / «Поведение», у каждого контрола видимое
  пояснение простым языком, «Конфиг с сервера» свёрнут, пока URL не задан, а кнопка «Сохранить и
  применить» закреплена внизу и не уезжает под скролл.

  Режим и «Проксировать весь трафик» были двумя независимыми контролами, хотя выбор по смыслу
  один и тот же; теперь это один список из трёх вариантов, и каждый описан последствиями, а не
  словами allowlist/blocklist. Заодно чипы доменов перестали печататься капсом — редактор чипов
  наследовал `text-transform` от ярлыка поля, на подсетях из цифр это было не видно.


- **Байпас роутерного FakeIP стал opt-in, собственный fake-ip остаётся `198.18.0.0/15`.**
  В коротко живших 0.2.x диапазон `198.18.0.0/15` попал в bypass по умолчанию, а свой
  fake-ip был принудительно уведён на `240.0.0.0/15` (Class E). Это оказалось неверным
  разменом:

  - смена fake-ip — ломающая операция: адреса, уже закэшированные приложениями,
    обесцениваются, и трафик умирает до перезапуска приложения;
  - ради сценария с FakeIP-роутером (нужен меньшинству) миграция навязывалась всем, да
    ещё и молча, через авто-обновление — отсюда «внезапно перестало работать без каких-либо
    изменений» при зелёной диагностике;
  - Class E не проверен на всех сборках Windows — это была отложенная мина.

  Теперь по умолчанию исключаются только заведомо непроксируемые диапазоны
  (`127.0.0.0/8`, `169.254.0.0/16`, `224.0.0.0/4`, `255.255.255.255/32`), а связка для
  FakeIP-роутера включается явно двумя ключами (`bypass_cidrs` + `dns.fakeip_v4`) —
  рецепт в README. Валидация по-прежнему не даёт исключить из туннеля собственный
  fake-ip и подсказывает рекомендованный диапазон.

  **Возврат автоматический.** Конфиг, оставшийся от 0.2.6/0.2.7, распознаётся по паре
  «`dns.fakeip_v4: 240.0.0.0/15` + список `bypass_cidrs`, в точности равный их дефолту»:
  такие значения записаны программой, а не человеком, поэтому роутерный диапазон убирается
  из исключений, а fake-ip возвращается на `198.18.0.0/15`. Конфиг, где `bypass_cidrs`
  правили руками (набор отличается от того дефолта), считается осознанной настройкой под
  FakeIP-роутер и не трогается.

  > В 0.2.8 этот возврат не срабатывал: наличие `198.18.0.0/15` в списке принималось за
  > признак ручной настройки, хотя ровно эту строку туда записали сами 0.2.6/0.2.7. В
  > результате обновившиеся оставались на Class E — исправлено.

  Разово после возврата приложения, успевшие закэшировать адрес из `240.x`, нужно
  перезапустить (плюс `ipconfig /flushdns`). Дальше такого не повторится: таблица
  fake-ip теперь переживает перезапуски движка (см. выше).

### Совместимость

- Старые конфиги без `bypass_cidrs` продолжают работать и получают список по умолчанию.
- Поведение остального трафика не изменилось — он по-прежнему идёт в прокси.
