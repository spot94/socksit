# Изменения

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/);
проект придерживается [семантического версионирования](https://semver.org/lang/ru/).

## [Не выпущено]

### Добавлено

- **Bypass-подсети (`bypass_cidrs`)** — перечисленные диапазоны исключаются из туннеля
  целиком: для них ставятся более специфичные маршруты через физический шлюз, которые
  выигрывают у `0.0.0.0/0` по longest-prefix-match независимо от метрики. Реализовано
  через `route_exclude_address` на TUN-интерфейсе плюс страховочное правило маршрутизации
  в direct.

  Значения по умолчанию (работают из коробки, настройка не требуется):
  `198.18.0.0/15`, `127.0.0.0/8`, `169.254.0.0/16`, `224.0.0.0/4`, `255.255.255.255/32`.

  Настраивается ключом `bypass_cidrs` в `socksit.yaml` и командами
  `socksit config bypass add|rm|list|reset`. Отсутствие ключа = значения по умолчанию,
  `bypass_cidrs: []` = отключить их.

### Исправлено

- **«Конфиг ещё не валиден: field bypass_cidrs not found» после обновления.** Разбор
  конфига отвергал любой незнакомый ключ. Как только более новая версия дописывала в
  `socksit.yaml` новый ключ (первым таким стал `bypass_cidrs`), любой компонент постарше —
  панель, запущенная из старой копии exe, откат на предыдущую версию, фид от более нового
  конфиг-сервера — переставал читать конфиг целиком: служба отказывалась применять
  собственный файл, проксирование останавливалось, а панель показывала «Конфиг ещё не
  валиден».

  Теперь незнакомые ключи игнорируются (конфиг совместим вперёд и назад), но не
  замалчиваются: `socksit config validate` и «Диагностика» показывают их предупреждением —
  это либо опечатка, либо запись от более новой версии.

- **Приложение пропадает из «Статистики» и начинает работать только после его
  перезапуска.** Таблица соответствий fake-ip жила только в памяти движка, поэтому любой
  перезапуск движка (сохранение настроек, обновление управляемого конфига, смена сети)
  обнулял её. Приложение, закэшировавшее выданный ранее fake-ip адрес, после этого било в
  адрес, про который новый движок ничего не знает: трафик никуда не шёл и в статистике не
  появлялся, пока не перезапустишь само приложение.

  Теперь состояние движка сохраняется на диск (`experimental.cache_file` со
  `store_fakeip`, файл `%ProgramData%\SocksIt\cache.db`) — соответствия переживают
  перезапуск, и перезапускать приложения больше не нужно.

- **«Повисший» значок в трее после включения компьютера.** Служба запускала трей, как
  только появлялся пользовательский токен — то есть ещё на экране входа, до старта
  `explorer.exe`, который владеет областью уведомлений. Регистрация значка
  (`Shell_NotifyIcon`) в этот момент штатно завершается таймаутом, библиотека трея
  начальную попытку не повторяет: процесс оставался жив, но без значка и меню — пустая
  иконка, не реагирующая на нажатия, — и при этом удерживал синглтон, поэтому служба его
  не перезапускала.

  Теперь трей запускается только после того, как в целевой сессии поднялся и «устоялся»
  (5 c) shell, а сам трей завершает работу, если значок не зарегистрировался за 30 c —
  служба поднимает его заново уже в готовой сессии.

- **Совместимость с роутерным прозрачным проксированием по FakeIP.** Если роутер
  (OpenWrt + Podkop/sing-box, mihomo, clash) отдаёт синтетические адреса из
  `198.18.0.0/15`, SocksIt перехватывал их своим маршрутом по умолчанию и уводил в TUN
  вместо роутера — сайты из «туннельных» списков роутера переставали открываться
  («Connection refused»), пока служба запущена. Теперь `198.18.0.0/15` исключён из
  туннеля по умолчанию.

### Изменено

- **Байпас роутерного FakeIP стал opt-in, собственный fake-ip остаётся `198.18.0.0/15`.**
  В коротко живших 0.2.x диапазон `198.18.0.0/15` попал в bypass по умолчанию, а свой
  fake-ip был принудительно уведён на `240.0.0.0/15` (Class E). Это оказалось неверным
  разменом:

  - смена fake-ip — ломающая операция: адреса, уже закэшированные приложениями,
    обесцениваются, и трафик умирает до перезапуска приложения;
  - ради сценария с FakeIP-роутером (нужен меньшинству) миграция навязывалась всем, да
    ещё и молча, через авто-обновление — отсюда «внезапно перестало работать без каких-либо
    изменений» при зелёной диагностике;
  - Class E не проверен на всех сборках Windows — это была отложенная мина.

  Теперь по умолчанию исключаются только заведомо непроксируемые диапазоны
  (`127.0.0.0/8`, `169.254.0.0/16`, `224.0.0.0/4`, `255.255.255.255/32`), а связка для
  FakeIP-роутера включается явно двумя ключами (`bypass_cidrs` + `dns.fakeip_v4`) —
  рецепт в README. Валидация по-прежнему не даёт исключить из туннеля собственный
  fake-ip и подсказывает рекомендованный диапазон.

  **Возврат автоматический:** конфиг, в котором `dns.fakeip_v4` равен ровно
  `240.0.0.0/15` (значение от той версии) и при этом `198.18.0.0/15` не байпасится,
  при загрузке возвращается на `198.18.0.0/15`. Осознанная настройка под роутер
  (байпас + Class E) сохраняется как есть.

  Разово после возврата приложения, успевшие закэшировать адрес из `240.x`, нужно
  перезапустить (плюс `ipconfig /flushdns`). Дальше такого не повторится: таблица
  fake-ip теперь переживает перезапуски движка (см. выше).

### Совместимость

- Старые конфиги без `bypass_cidrs` продолжают работать и получают список по умолчанию.
- Поведение остального трафика не изменилось — он по-прежнему идёт в прокси.
